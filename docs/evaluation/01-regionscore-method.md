# RegionScore 계산 근거

교수님 피드백(주간보고4)의 질문에 순서대로 답한다. 숫자는 `02`~`04` 문서의 실제 Google Routes 이동시간 실험에서 가져왔다.

## 1. 무엇을 계산하나

참여자 n명이 후보 지역(지하철역) 하나에 모일 때 참여자별 이동시간(분)이 정해지면, 세 지표를 구한다.

| 지표 | 뜻 | 왜 보는가 |
|---|---|---|
| 평균 이동시간 | 모두의 이동시간 평균 | 전체 효율 |
| 최대 이동시간 | 가장 오래 걸리는 사람의 시간 | 한 사람에게 부담이 몰리는 것을 막음 |
| 이동시간 편차 | 참여자 이동시간의 (모)표준편차 | 사람 사이의 공평함 |

```
RegionScore = 1 − ( w_avg × 평균′ + w_max × 최대′ + w_std × 편차′ )     (각 ′는 0~1로 정규화한 값)
```

가중치 합은 1이라서 점수는 0~1이고 **높을수록 좋다**. 구현은 `backend/app/scoring/region.py`(순수 함수), 가중치는 `backend/config/region.yaml`에 있다.

## 2. 서로 다른 단위·범위를 어떻게 합치나 (정규화)

세 지표는 모두 '분'이지만 범위가 다르다. 04번 예시(신촌+건대입구+사당, 후보 24곳)에서 평균은 18.4~27.2분, 최대는 21.9~45.9분, 편차는 1.2~14.6분이다. 그대로 더하면 변동 폭이 큰 지표(최대)가 점수를 지배한다.

그래서 **후보 지역들 사이에서 min-max 정규화**한다: `x′ = (x − 최솟값) / (최댓값 − 최솟값)` → 0(가장 좋음) ~ 1(가장 나쁨). 모든 후보의 값이 같으면 차이가 없으므로 전부 0으로 둔다.

- 장점: 단위·범위가 달라도 같은 눈금에서 비교되고, 가중치가 '얼마나 중요한가'를 그대로 뜻한다.
- **한계(중요)**: 정규화가 후보 집합에 상대적이다. 후보 풀이 바뀌면 점수와 순위가 조금 바뀔 수 있다. 서비스는 1단계로 추린 후보(shortlist) 안에서 다시 정규화하기 때문에, 후보를 몇 곳 뽑느냐에 따라 결과가 달라질 수 있다(`02` 문서 마지막 '점검' 절).

## 3. 가중치는 어떻게 정했나 (현재 상태를 솔직하게)

현재 기본값은 **평균 0.4 / 최대 0.3 / 편차 0.3** 이고, **설계자가 정한 잠정값**이다. 근거는 다음 설계 의도뿐이다.

- 평균은 가장 직관적인 효율 지표라 가장 큰 비중을 둔다.
- 최대와 편차는 '평균만 보면 한 사람이 희생된다'는 문제를 막는 장치라 합쳐서 0.6을 준다.

사용자 조사나 평가로 검증한 값이 **아니다.** 조정 절차는 `05-evaluation-plan.md`와 `06-survey.md`에 정해 두었다 (AHP 쌍대비교 + 100점 배분 설문 → `scripts/analyze_survey.py`로 가중치 계산 → 민감도 확인 후 반영). 설문 응답이 모이기 전까지는 이 값을 '확정'이라고 주장하지 않는다.

## 4. 가중치를 바꾸면 순위가 얼마나 달라지나

`03-sensitivity.md`: 합이 1인 모든 조합(0.1 간격 66가지)으로 같은 실제 이동시간 데이터를 다시 점수화했다.

| 시나리오 | 1위가 기본과 같은 비율 | 상위 3곳이 같은 비율 | 평균 켄들 타우 |
|---|---|---|---|
| 홍대입구 + 잠실 (2명) | 68% | 89% | 0.77 |
| 신촌 + 건대입구 + 사당 (3명) | 80% | 36% | 0.80 |
| 노원 + 강남 + 신도림 (3명) | 92% | 61% | 0.79 |
| 수원 + 의정부 (2명) | 95% | 44% | 0.79 |
| 홍대입구 + 강남 + 노원 + 신도림 + 왕십리 (5명) | 80% | 67% | 0.83 |

읽는 법: 가중치를 아무렇게나 바꿔도 **1위는 68~95%의 조합에서 그대로**다(기본값 근처에서 비교적 안정적). 반면 **2·3위는 가중치에 민감**하다(상위 3곳이 같은 비율이 36~89%). 따라서 1위 추천은 가중치 오차에 어느 정도 강하지만, 후보 목록 전체를 보여줄 때는 설문으로 가중치를 맞추는 일이 의미 있다.

## 5. 평균 이동시간만 보는 추천보다 어떤 장점이 있나

`02-baseline-comparison.md` (5개 시나리오, 실제 이동시간):

| 방식 | 평균(분) | 최대(분) | 시간 차이(분) |
|---|---|---|---|
| MeetPick (실제 흐름) | 29.5 | 32.1 | 7.2 |
| 평균 이동시간만 | 27.0 | 35.8 | 17.4 |
| 지리적 중간점 | 35.2 | 40.2 | 9.7 |
| 대표 번화가 중 최선 | 29.5 | 42.7 | 26.7 |

- 평균만 보면 평균은 2.5분 더 짧지만, **가장 힘든 사람은 3.7분 더 걸리고 사람 사이 시간 차이는 2.4배**(7.2 → 17.4분)다. 노원+강남+신도림에서는 평균만 보는 추천(사당)이 평균 27.2분이지만 한 사람이 49.9분 걸렸다(MeetPick은 최대 29.4분).
- 이것이 평균이 아닌 '이동 부담'을 반영한 차별성이다. 단, 평균은 약간 희생한다는 점도 사실이다.

## 6. 인원 수 확장

2명부터 5명까지 입력할 수 있다(`schemas.py`, 프론트 `MAX_PARTICIPANTS`). 평가 실험에 2·3·5명 시나리오를 모두 넣었고 계산은 인원에 관계없이 같은 식이다. 주의할 점:

- 2명이면 편차는 두 시간 차이의 절반이라 '최대'와 '편차'가 거의 같은 정보를 준다. 인원이 늘수록 세 지표가 서로 다른 정보를 갖는다.
- 5명 시나리오에서는 전원의 이동시간을 맞추기가 어려워, MeetPick 추천도 가장 오래/적게 걸리는 사람의 차이가 23.4분이었다(`02` 5명 표. 같은 시나리오의 대표 번화가 방식은 38.5분). 인원이 늘수록 '공평함'의 기준값(`config/region.yaml`의 `fairness_levels`)도 달라질 수 있어 사용자 평가로 조정이 필요하다.

## 7. 실제 교통 데이터 연결

- 서비스: 1단계(API 호출 0)로 지하철 그래프 추정 후 상위 8곳을 고르고, 2단계에서 Google Routes `computeRouteMatrix`(버스 포함 대중교통, 약속 시간 도착 기준)를 **검색당 1회** 호출해 실제 이동시간으로 RegionScore를 다시 계산한다.
- 평가: `scripts/evaluate.py collect --run`으로 출발지×후보 전체의 실제 시간을 수집했다 (시나리오 5개, 호출 6회, 361칸). 교수님이 요청한 **출발지 3 × 후보 3** 계산 예시는 `04-3x3-example.md`에 실제 시간과 계산 과정 전체를 적었다.
- 한계: 이동시간은 약속 시간(토요일 18시) 한 시점의 값이다. 다른 요일·시간대의 결과는 다를 수 있다.

## 8. 화면의 점수가 뜻하는 것

- **이동 공정성 높음/보통/낮음**: 가장 오래 걸리는 사람과 가장 적게 걸리는 사람의 차이가 5분 이하/12분 이하/초과 (`region.yaml`, 잠정 기준).
- **RegionScore**: 위 1절의 점수. 화면의 "점수는 이렇게 계산돼요"를 펼치면 지표별 값, 정규화 값, 가중치, 점수 기여가 나온다.
- **PlaceScore**(장소): 접근성·평점·리뷰 수·목적 적합·연령 적합 5개 항목(각 0~1)의 가중합. 장소 카드의 "점수 보기"에서 항목별 점수와 기여를 볼 수 있다. 평점이 없는 장소는 사전 평균 평점과 리뷰 0으로 계산하고 화면엔 "평점 정보 없음"으로 표시한다(가짜 평점 없음). 연령 적합 점수는 임의값이라 `*`로 표시한다.
