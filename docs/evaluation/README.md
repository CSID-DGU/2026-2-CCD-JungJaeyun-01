## 재현 방법

```bash
cd backend
python scripts/evaluate.py collect          # 호출 계획만 출력 (API 호출 없음)
python scripts/evaluate.py collect --run    # 실제 이동시간 수집 (Google Routes 6회, 361칸) → docs/evaluation/data/
python scripts/evaluate.py analyze          # 저장된 데이터로 02~04 문서를 다시 생성 (API 호출 0)
python scripts/survey_to_csv.py 받은파일.csv -o 응답.csv   # 구글폼 응답 시트(또는 응답 코드 txt)를 분석용 CSV로
python scripts/analyze_survey.py 응답.csv    # 설문 응답으로 가중치 계산
```

시나리오·허브 목록은 `backend/config/evaluation.yaml`에서 바꾼다.

## 알아둘 한계

- 이동시간은 2026-11-07(토) 18시 도착 기준 한 시점의 값이다.
- 시나리오 5개의 작은 실험이다. 02 문서 마지막 '점검' 절: 서비스의 1단계 후보 수(8곳)가 부족해 최선을 놓친 경우가 1/5(수원+의정부, 평균 +8.7분)였다. 후보를 12곳으로 늘리면 그 경우는 고쳐지지만 다른 시나리오에서 근소한 차이(평균 0.5분)가 생기고, 16곳이면 5/5가 최적과 같았다. 정규화가 후보 집합에 상대적이기 때문이다. 후보 수를 늘리는 변경은 요청 칸 수(과금)가 늘어서 적용하지 않고 기록만 해 두었다.
- 사용자 만족도는 아직 측정하지 않았다. 이 문서의 비교는 이동시간 기준이다.
